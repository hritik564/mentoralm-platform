# Unified-platform architecture

## Confirmed direction

MentoraLM is one platform with multiple product surfaces and an eventual unified identity model. Website is first; Dashboard, LMS, and Admin remain deferred unless explicitly requested. The W1/W2 public frontend selection is recorded below; deployment topology and future domain infrastructure remain undecided.

Prefer a modular architecture with explicit boundaries over premature microservices. Modules can share infrastructure while preserving ownership and contracts; separate services are not required for separate responsibilities.

## Conceptual boundaries

| Boundary                       | Responsibility                                                        | Interaction principle                                            |
| ------------------------------ | --------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Public website presentation    | Public content, discovery, journey entry points                       | Consume approved contracts; do not reach into learning internals |
| Student Dashboard presentation | Student overview and navigation                                       | Display domain-owned state; do not become its source of truth    |
| Learning domain / LMS          | Content, progress, assessments, learning outcomes                     | Own learning state and expose deliberate contracts               |
| Operational domains            | Applications, enrollment, student operations                          | Assign exact ownership and lifecycle in later domain design      |
| Admin control plane            | Authorized management operations                                      | Invoke domain operations through backend permission checks       |
| Shared platform capabilities   | Identity, authorization, storage, backend and database infrastructure | Assign explicit owners and interfaces when designed              |

This is a responsibility map, not a package layout, service list, database schema, or permission model.

## Dependency and state rules

- Business rules belong to domains, outside presentation components.
- Public program information must not require website code to access private learning tables or internal progress models. Design public contracts when implementation is authorized.
- Dashboard may display learning progress from the learning domain, but must not maintain an independent authoritative progress record.
- Enrollment controls learning access. Its lifecycle and relationships require explicit design; no status rules are assumed here.
- Program and Course are distinct concepts in Program → Course → Section → Lesson. Cardinalities and reuse rules remain undecided.
- Identity can be shared across surfaces while authorization differs by action, resource, and ownership.
- Shared database or storage infrastructure must not grant unrestricted access across domains. Avoid unnecessary state duplication.

## Evolution and decisions still required

The public frontend stack is now selected. Choose hosting, identity integration, data/storage approach, future domain module layout, and operating model deliberately when authorized. Preserve room for later integrations without building speculative infrastructure today. Record approved choices in [Decisions](DECISIONS.md); apply [Security](SECURITY.md) at each trust boundary.

## W1/W2 frontend implementation

Next.js 16 App Router with React 19 and strict TypeScript renders the public homepage as static prerendered HTML. Next.js was chosen for public rendering, metadata, image optimization, reusable React composition, and room for future API/authenticated integration. A client-only Vite SPA would require additional public-rendering/SEO plumbing; an HTML-only implementation would give up the component and type foundation requested for the evolving platform. No future backend or authentication architecture is implied. See the [official rendering documentation](https://nextjs.org/docs/app/getting-started/server-and-client-components).

`src/app` composes the page and metadata. `src/components/home` owns narrative sections; layout, navigation, program, motion, and UI components have separate responsibilities. `src/content/programs.ts` owns the seven editorial module positions. `src/content/home.ts` owns shared navigation, journey content, opportunity categories, and future-feature notices. `src/lib/site.ts` validates the optional approved public origin. CSS tokens and shared styles live in `src/styles`. Assets are local under `public`.

Presentation is server-rendered by default. Navigation, native notice dialogs, the reveal observer, and the R2 hero's small motion interaction wrapper are client components. Their state is transient UI state; it is not identity, authorization, enrollment, or learning state. Navbar accepts an account-actions presentation slot for later integration, without inventing an authenticated user model. No API routes, Server Actions, persistence, CMS, ORM, or identity provider were added.

R2 keeps hero editorial content, local imagery, capability links, Menti SVG, and decorative pathways in server components under `components/home/hero` and `components/menti`. `HeroExperience` receives those rendered children and owns only pause state, the reduced-motion subscription, and throttled fine-pointer eye movement. Menti is reusable presentation, not an AI service, identity symbol, or authenticated product integration. Hero CSS is scoped to its own composition; shared navigation and other homepage sections remain unchanged.

The subsequent Menti depth/blink correction adds `MentiInteraction`, a small client button receiving the server-rendered SVG as children. It owns only the explicitly requested blink, using the browser's Web Animations API on the existing eye group. A new activation cancels the previous effect; completion and unmount release it. No interaction state, timers, additional dependencies or character geometry move into the client component. Its button remains disabled until hydration, keeping the static character visible without JavaScript. It adds no AI or dialog functionality.

## D2 course presentation and learning handoff

The two protected route pages continue requiring D1 server identity. Overview composes a welcome using the provider first name, Continue Learning, course preview, four shortcuts and a D3 resource boundary. My Courses owns only local Enrolled/Viewed tab selection. D1 shell, auth and public scenes are unchanged; D2 styles are isolated in `dashboard-courses.css`.

`lib/dashboard/courses.ts` defines discriminated Viewed/Enrolled snapshots and an empty source seam. D4 must replace that source with an authenticated, per-student domain adapter, including ownership checks and validation of metadata, image sources and timestamps. The adapter owns ordering; presentation does not calculate learning progress, save viewing history or create enrollment records. Status names describe display states, not an enrollment lifecycle policy. Course cards show validated supplied progress and timestamps without creating missing values.

`LearningLaunchTarget` contains a destination identifier, never a student-supplied URL. `learning-launch.ts` maps it through deployment-owned configuration, allowing strict local paths or exact trusted HTTPS origins. Unknown identifiers, protocol-relative paths, credentials, encoded/traversal paths and query/fragment redirects fail closed. The runtime registry is empty until an LMS deployment is approved; unavailable destinations render explanatory text without a launch link. Changing deployment configuration can relocate LMS without changing presentation components. Public course links have a separate local discovery-path validator.

Resolving a link is not authorization. The future LMS must verify identity, course ownership/enrollment and applicable access policy at its own server boundary. Dashboard receives progress snapshots only; lesson, quiz, assignment, assessment and attendance state remain in the learning domain. No LMS, launch endpoint, token exchange, business persistence or tracking API is introduced in D2.

## D3 student surfaces and theme

The existing four protected routes now compose Resources, Support, Referral and Profile; proxy/session guards remain unchanged. Resource, support and referral sources return empty records until D4. Their typed snapshots are not persistence, enrollment policy or authorization.

- **Resources:** Admin alone creates/uploads/manages records. Student presentation searches the supplied authorized set and exposes permitted preview/download capabilities. A deployment-owned resource registry resolves target IDs to strict local paths or exact trusted HTTPS origins. The default registry is empty. React escapes plaintext; image preview accepts raster MIME types only; PDF preview uses a sandboxed, script-disabled frame. Unsupported formats remain download-only. A shared native dialog owns Escape, focus containment/restoration and body-scroll cleanup.
- **Support:** Centrally configured categories and four status labels support reusable composer/list/row/detail/conversation views. Drafts exist only in component memory. Validation errors connect to fields. The explicit unavailable service never sends/saves a ticket or reply and reports that fact. D4 must implement authenticated operations and server ownership checks for every list/read/reply; client IDs/filtering do not authorize access.
- **Referral:** Server-issued code/link snapshots and neutral invitation status history are presentation only. Exact trusted origins and an invite path validate configured links. Clipboard/Web Share adapters handle success, cancellation, errors and copy fallback. Runtime has no code/link; no client-generated identity or economics.
- **Profile/settings:** A server-only projection extends the existing verified identity with provider last name and primary phone. No provider IDs, passwords or fabricated education fields enter this view. Clerk's `openUserProfile` owns editing/security; its portal stays inside Dashboard and receives current semantic colors. Education, notifications and privacy preferences are visibly deferred within Profile; sidebar remains six items.

`DashboardTheme` owns transient Light/Dark selection. The preference cookie has Dashboard path, one-year lifetime, SameSite=Lax and Secure on HTTPS; it carries only a validated theme value, never identity or permissions. The protected server layout reads it before rendering the shell's scoped data attribute. Default Light preserves D1/D2 styling; Dark supplies deliberate navy/elevated surfaces through semantic CSS variables. Existing layouts and interactions remain unchanged. No marketing tokens/root attributes are modified. D4 may replace device preference with an account preference under an explicit synchronization policy.

D3 fixture components are bundled only in the test harness using existing tooling. No test route, persistence API, business database, Admin, LMS, payments, certificate generation or notification delivery is added.

## D4 — MentoraLM business persistence

D4 supersedes the runtime-empty D2/D3 adapters. Clerk remains the identity/session authority; PostgreSQL and Prisma 7 own MentoraLM business data. `lib/db` lazily validates/connects through the PostgreSQL driver adapter. Generated server client files are ignored and rebuilt during install/build. `lib/student/session` maps a verified Clerk subject to a unique internal User with STUDENT default; idempotent provisioning retries unique conflicts. No email mapping, password storage, metadata database or webhook is used.

`lib/student/repository` is the ownership boundary; its actor comes from the verified server mapping. Services project narrow presentation contracts for server-rendered Dashboard pages and private APIs. Client components use APIs only for mutations and ticket detail, with announced feedback and refresh after writes. Infrastructure errors render unavailable states rather than empty substitute records. Summaries are bounded at 100 rows; ticket detail at 200 messages. Pagination is a later extension.

Program and Course are separate models. CourseView upserts each user/course pair; Enrollment has one user/course relationship and restrained ENROLLED/IN_PROGRESS/COMPLETED status. Enrollment creation is not exposed to students. All LMS progress, next lesson and learning targets remain null. No sections, lessons or assessment tables are introduced.

Resources remain Admin-owned: published records are accessible through global STUDENTS audience, explicit student assignment, or COURSE/PROGRAM audience with the student's enrollment. All three current enrollment statuses retain resource access; revocation/cancellation policies are deferred. Private unassigned and unpublished records are denied. Delivery reauthorizes each request and reads a controlled private local-file provider. Optional `RESOURCE_FILES_ROOT` is outside `public`; absent configuration means no delivery capability. No object-storage provider or upload API is invented.

Support stores owner-scoped tickets/messages; student creates OPEN tickets and replies only to OPEN/IN_PROGRESS tickets. Actor/sender are fixed server-side. Serializable reply transactions coordinate future status changes. Referral uses a random unique code, an immutable one-referrer attribution per referred account, and real Joined history without exposing another student's identity. `/invite/[code]` is a minimal functional entry; signed-in users confirm attribution in Dashboard. Signed-out users must return to the invitation after authentication. It never mutates on GET.

MentoraLM stores education/institution/year/interests/goals; Clerk continues to own identity/contact/security. The Dashboard device theme cookie is unchanged; account synchronization is not implemented. Admin role has no implemented business mutations and cannot use the Student repository. Administrative workflows, resource publication/scanning, enrollment lifecycle and LMS remain separate future domains.

## L1 — LMS learning foundation

The approved LMS lives in this application under `/learn`, `/learn/lectures`, `/learn/assignments`, `/learn/resources`, `/learn/discussions`, `/learn/chat` and `/learn/courses/[courseId]`. Existing Clerk/proxy/page guards protect the route family; the approved redirect allowlist adds only those routes and strict internal course paths. LMS server repositories require the same mapped STUDENT User. LMS entitlement is required before any workspace read. Course access additionally requires a published Course and that student's Enrollment; all three existing enrollment statuses retain outline access. Batch membership never grants enrollment. Unknown/foreign course routes show the same unavailable/not-found surface.

Program != Course. Course → ordered Section → ordered mixed LearningItem establishes the curriculum domain. Items have LESSON/QUIZ/ASSIGNMENT/RESOURCE/LIVE_SESSION/ASSESSMENT type and publication state; only published sections/items are projected. Lesson is a minimal one-to-one metadata subtype with format, optional storage key and duration. Composite foreign keys/checks prevent attaching Lesson metadata to another item type. No item playback, completion, submissions, attempts, attendance or progress state is introduced. LMS alone will own those later.

`User.studentId` is a unique, immutable operational identifier, never an auth key. PostgreSQL issues `MLM-STU-YYYY-NNNNNN` from a global bigint sequence using UTC issuance year, with at least six serial digits and no yearly reset. Insert/update triggers issue IDs for STUDENT records, reject explicit IDs/changes, and non-destructively backfill existing students. Primary keys and Clerk mapping remain unchanged. Sequence gaps are valid. Identity is projected only in LMS Home; Dashboard/public/account payloads do not add Student ID or batches.

Batch has a unique human-readable code, status/dates and optional Program **or** Course scope; unscoped delivery contexts are supported. BatchMembership is a unique student/batch relationship with ACTIVE/INACTIVE status, joined/left timestamps, no self-assignment APIs and no enrollment duplication. Current batch is ACTIVE with ACTIVE membership inside inclusive dates; latest start wins and code breaks ties, null starts last. Other memberships remain visible. Future date/status controls are server-owned.

INSTRUCTOR is a distinct role, not ADMIN. BatchInstructor supports multiple instructors per batch. Role-aware composite foreign keys and checks require STUDENT memberships and INSTRUCTOR assignments; roles cannot be changed while incompatible relationship rows remain. Future Admin workflows must explicitly resolve those relationships before role transitions. No instructor-facing or authoring UI is created.

Dashboard handoff uses server-derived enrollment snapshots and strict internal `lms-course-<courseId>` targets. Existing cards/Continue Learning can now open the authorized internal course outline with null progress. The resolver is never an access grant: LMS rechecks enrollment every request. Completed-course Dashboard presentation remains unchanged, while LMS outline access follows the existing enrollment policy.

The LMS is intentionally dark-first with its own scoped presentation tokens, horizontal primary navigation and two-level Learn navigation. Mobile uses a two-row app bar and wrapped subnav; tablet uses intermediate spacing/stacking. No second preference store or theme toggle is added; Dashboard cookie/preferences and public theme are unchanged. Account links reuse the existing protected profile flow. Chat/Assignments/Resources/Discussions explicitly describe later functionality. No new mascot, messaging service or runtime seed.

Future communications use Batch → Memberships → audience resolution → shared Communications Service. Membership identifies an operational audience, never marketing consent. Operational and marketing permission must be evaluated separately at send time; no communication provider/sending or consent field is added in L1.

## L1 domain/access addendum

Locked production topology: `mentoralm.com` public website and module/product `/<module-slug>` pages, `mentoralm.com/dashboard` Student Dashboard, and `students.mentoralm.com` LMS. These are one application, Clerk instance and MentoraLM PostgreSQL User. `lib/platform/domains` validates approved deployment origins, builds controlled handoff/support/account links and maps LMS-host `/`, `/lectures` and `/courses/[courseId]` to internal `/learn` routes. The local same-host `/learn` route remains available when domain configuration is unset. Host selection is routing only, never an authorization grant. No DNS, deployment or module-page implementation is included.

Authorization is Clerk session → MentoraLM STUDENT User → LMS entitlement → own Enrollment → published Course. Entitlement belongs to PostgreSQL: nullable `User.lmsAccessOverride` means inherited (null), ENABLED or DISABLED; `Batch.lmsAccessEnabled` defaults false. A student override always wins. Without an override, any applicable enabled batch grants LMS access: ACTIVE membership, joined timestamp reached, no elapsed left timestamp, ACTIVE batch and inclusive optional start/end dates. Disabled batches do not veto another applicable enabled batch. No applicable grant means deny. Current-batch display selection is presentation and does not determine entitlement. An enabled override grants workspace access without a batch but never grants a course enrollment.

Layout and every LMS repository read enforce entitlement; course queries also include entitlement in their ownership predicate. Decisions are request-local, not persisted in Clerk metadata or cached across sessions. Business-data revocation takes effect on subsequent requests without logout. Denied students see an intentional access-unavailable surface with Support, without override/batch/reason details or Student ID. Dashboard access remains independent. Students have no entitlement, batch, instructor-assignment or enrollment mutation API. Future audited Admin controls may change these settings; no Admin UI is built. Student ID and Batch information remain LMS-only.

## L2 — Course player, delivery and lesson progress

The existing dark-first LMS shell now hosts a course overview and `/learn/courses/[courseId]/lessons/[lessonId]` player, also mapped to `/courses/[courseId]/lessons/[lessonId]` on the approved LMS host. Server projections supply ordered published Section/Item metadata plus the current student's state; selected Lesson content is loaded separately and binaries never pass through React. Desktop outline/current content, tablet/mobile native modal outline, explicit Previous/Next and completion retain the L1 navigation. Future item types remain visible but cannot be completed or launched as lessons.

Lesson formats share one model: bounded, versioned typed text blocks; native video with optional protected WebVTT captions; sandboxed PDF with a separate-tab fallback and configurable download action; raster images with alt text; deployment-owned approved external target IDs. React escapes text, never interprets stored HTML. `lib/storage/private-files` provides bounded private file opening, path/symlink checks, signatures and streaming/range responses. Dashboard Resource and LMS Lesson/LearningResource permission checks remain separate. `LMS_FILES_ROOT` is an optional operator-controlled local provider; durable object storage remains a future production adapter.

LessonState is unique per User/Lesson and stores first/last access and nullable completedAt. Client navigation sends one same-origin access POST per selected lesson rather than writing from GET/server rendering/prefetch. Server-derived identity, publication, entitlement and enrollment are rechecked in serializable transactions; bounded retries make repeated/concurrent completion idempotent. Completion timestamps remain stable. Completion is manual: no watch percentage, scoring, telemetry or Enrollment status change. Subsequent requests reauthorize against current business data.

`lib/lms/progress` is the aggregation boundary: L2 counts only required, published LESSON items with Lesson metadata and manual semantics. Optional completion is recorded but excluded from the denominator/numerator. Draft sections/items and unsupported future types contribute nothing. Zero required lessons yields null percentage, not fabricated 100%. Section/course projections derive counts and rounded percentages from own state. Publishing changes recalculate totals. Future quiz/assignment/assessment completion contributors must extend this boundary; lesson progress 100% is not final academic course completion/certification.

Continue Learning resumes the valid most recently accessed incomplete lesson, then first incomplete required lesson in curriculum order, then incomplete optional lesson, then overview. Ties use lesson ID; courses order by actual last access then course ID. Dashboard reads this same narrow projection and controlled course/optional-lesson target, never writes or recalculates completion. Denied LMS access suppresses learning projections/launch actions without denying Dashboard itself.

LearningResource is a minimal RESOURCE item subtype in an authorized course section, with separate delivery/download metadata. It powers Learn → Resources and course-overview materials without entering Dashboard's general Resource table/library. Lesson attachment relationships, authoring/upload UI, full publication scanning, assessments, submissions, attendance, certificates, discussions and AI remain outside L2.

## L3 academic engine

QuestionBank owns reusable plain-text Question/QuestionOption records. AcademicActivity specializes an actual QUIZ or ASSESSMENT LearningItem through a constrained subtype relationship; shared execution machinery retains their distinct kinds and completion sources. Ordered ActivityQuestion associations carry points. AcademicAttempt/AcademicResponse/ResponseOption copy normalized prompt, options, scoring keys, weights and result policy at start. Student DTOs explicitly omit keys/explanations until configured post-submit review. Published activity and curriculum access are always rechecked. Assessment responses are a future analysis input; scoring does not produce psychological/career intelligence.

Assignments have separate metadata, per-student AssignmentSubmission and immutable numbered SubmissionVersion content/files. Version status and append-only reviewer records preserve history; the latest version alone supplies completion. Private uploads use generated opaque storage keys and a distinct server-owned root. AcademicStaff verifies persisted role and assigned Batch/Course/Program scope for review, attendance and reconciliation; no privileged HTTP/UI surface is exposed. Audit records accompany privileged changes.

BatchSession and membership-linked AttendanceRecord own delivery attendance. HELD sessions count only within membership and batch dates and current course access. Historical inactive membership records remain stored/readable while workspace/course access remains authorized. PRESENT and LATE count as attended; EXCUSED is removed from the denominator; UNRECORDED stays in it. RESOURCE and LIVE_SESSION do not acquire automatic item completion. An explicit Course-level attendance threshold may additionally gate final completion.

`course-projection.ts`, `progress.ts` and `completion.ts` are the single aggregation boundary: required published configured Lesson, Quiz, Assignment and Assessment contributors. Optional/unconfigured items are excluded; empty Courses cannot complete. `academicCompletionEnabled` is opt-in, preserving existing L2 Courses; `certificateEnabled` is a separate opt-in. Student mutations and scoped staff reconciliation evaluate final requirements in serializable transactions. Enrollment.completedAt preserves the first completion time. Added requirements can reopen status to IN_PROGRESS; read projections immediately reflect current eligibility even before the next reconciliation updates the materialized Enrollment row. Future publication/policy changes must invoke scoped reconciliation.

Certificate has one student/Course record and an unpredictable random code. Eligibility permits issuance, requalification may restore SUSPENDED, and staff REVOKED remains sticky. Current eligibility, entitlement and enrollment filter all certificate reads/downloads. A genuine attached private PDF may appear in Dashboard Resources through an authorized adapter, without copying storage; a record without a document has display only. Dashboard reads LMS final progress/next-item/completion/certificate projections and never scores, issues or changes learning state.

## L4 — final learning integration

Dashboard consumes the same `projectCourse`/`learningProjection`/attendance finalizer as the LMS. Real Lesson access, attempt start/save/submission and Assignment submission supply last learning activity. Resume is typed (Lesson, Quiz, Assessment, Assignment), uses the most recently active incomplete item or open attempt, then deterministic required curriculum order. Dashboard never writes learning state. Certificate projections require current entitlement/enrollment, current eligibility and ACTIVE status; only an attached authorized PDF appears in Dashboard Resources, from the original private storage key.

Discussions are Course conversations, optionally narrowed by Batch. Every read/create/reply verifies the verified student, current entitlement, own published Course Enrollment and applicable active membership when Batch-scoped. Creation validates that the Batch belongs to the Course/Program or is unscoped. Titles/posts are bounded escaped plain text. Author is server-derived; posts/context are immutable. List queries cap at 50 threads; conversation uses a 50-post cursor page with per-page authorization. Member labels avoid leaking identity/contact details. Support and future Chat remain distinct.

Batch communication planning is server-only: a persisted ADMIN or assigned INSTRUCTOR (operational only) resolves current active cohort memberships. Membership remains independent of LMS entitlement. EMAIL/WHATSAPP/IN_APP and OPERATIONAL/MARKETING are separate axes; absent permission means denied, even for operational/in-app channels. `CommunicationPreference` stores explicit permission/evidence with appended private audit history. No UI exposes unresolved policy. Future Course/Program/selected-student audience types require scoped resolvers; only Batch resolution is implemented. Message planning creates PENDING_PROVIDER or SUPPRESSED delivery records, never SENT, and performs no delivery. Templates/providers are deferred.

`LearningEvent` is a transactional fact journal with an idempotency key, kind, subject and optional Course/User context. Distinct QuizResultAvailable/AssessmentResultAvailable facts, Assignment reviews, first Course completion, Certificate issuance and Discussion replies write facts within their domain transaction. AssignmentPublished/SessionScheduled are typed future publication hooks; no publisher or worker is invented. No provider is called by academic services. A future consumer must reauthorize recipients and reread consent at dispatch, implement deduplication/retries and record genuine provider outcomes.

`AcademicAudit` remains the private shared LMS audit boundary. `LmsAccessAdmin` offers persisted-ADMIN-only, atomic audited student override, Batch LMS access and Enrollment changes; no HTTP/UI interface ships. Enrollment COMPLETED remains owned by academic reconciliation. Existing Instructor review/attendance and Admin certificate revocation retain scope checks. New consent audit details retain before/after permission/evidence.

`LIVE_SESSION` is optional curriculum context; a `BatchSession` may reference it plus the matching Course. Many cohort sessions need no curriculum item. Session attendance is not automatic Lesson completion. No meeting provider is configured. The root Course/Enrollment remains the learning authority.

Queries use owner/enrollment and published curriculum constraints, membership status indexes, unique student/item/attempt/version/certificate relationships, thread Course/Batch update indexes and thread post time/id index. L4 adds the targeted student/submittedAt index for the Home recent-result query. Shared projections batch attendance membership loading; neither discussions nor Home issue per-thread/member queries. Lists remain intentionally bounded; full catalog/thread-list pagination is future scale work.
