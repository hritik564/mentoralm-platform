## Neon connections, TLS and Prisma authority

Preserve pg + PrismaPg + singleton bounded application pool; no serverless driver. Both runtime and migration use the **direct** Singapore Neon endpoint. Runtime uses DATABASE_URL; a controlled, separately approved operator environment uses MIGRATION_DATABASE_URL, potentially with different credentials. Both must target the same explicit database, endpoint and public schema; hostname/port/name equality is checked. Do not put migration credentials on the serving VM. Pooler hosts ending `-pooler` are rejected for both. Neon PgBouncer uses transaction pooling, which cannot preserve arbitrary session settings/advisory locks; direct connections preserve current semantics, including Prisma serializable interactive transactions, transaction advisory locks, session locks and named prepared statements. [Neon pooling](https://neon.com/docs/connect/connection-pooling).

Use dashboard-issued direct hostname, not a guessed endpoint. Accepted host shape is ep-…[.c-N].ap-southeast-1.aws.neon.tech, port 5432/default. Configuration requires authenticated PostgreSQL URL, expected PRODUCTION_DATABASE_NAME, schema public/default, `sslmode=require&sslaccept=strict`, and no other query overrides. Runtime/operator pg strips URL SSL switches and passes `ssl: { rejectUnauthorized: true }`; Node validates public CA chain and endpoint hostname. Never disable verification or substitute an IP. Neon uses public certificates; ensure the maintained host CA bundle trusts its current chain (documented ISRG Root X1). Prisma CLI uses its validated strict URL; psql/pg_dump require a separate libpq connection configured `sslmode=verify-full`, with PGSSLROOTCERT pointing to a maintained public CA bundle, since sslaccept is not a libpq parameter. Never paste/print either connection string. No live TLS handshake was tested. [Neon secure connection](https://neon.com/docs/connect/connect-securely).

Initial application pool recommendation: **8 per Node process**, configure DATABASE_POOL_MAX 1–30, connect 5000ms, idle 10000ms, query/statement 10000ms. Total direct connections = VM processes × pool max + migration/backup/monitoring headroom; verify Neon plan capacity and reserve at least operator/backup slots before launch. No additional connection-lifetime override is introduced: direct pg idle eviction already bounds unused sockets, and lifetime tuning without observed provider behavior could cause unnecessary churn. Keep the 5-second connect limit initially; measure cold starts and consider disabling paid-plan compute suspension if approved rather than removing timeouts. Disconnect/query failures return existing generic errors; do not blindly retry non-idempotent writes. Future workers/instances require recalculating capacity.

Fresh Neon projects normally have a root branch, database neondb (unless named differently) and public namespace; Neon-owned metrics extension is documented in the system-owned postgres database. Choose a separate application database such as mentoralm_prod; never use postgres. These are documentation findings, not inspection of an actual newly created project. [Databases](https://neon.com/docs/manage/databases), [Neon extension](https://neon.com/docs/extensions/neon).

The first application preflight requires an empty unbaselined public namespace. PostgreSQL system objects outside public are not application drift; **no provider exception exists inside public**. Relations, functions, types, extensions, collations, operators and conversions in public all block installation without history. If provisioned Neon inserts any such object before MentoraLM migrations, stop and report; do not baseline it or delete it silently. Existing migration history must be the exact known successful checksum prefix; unknown/changed/failed/duplicate/gapped history denies. Only committed eleven migrations may run through guarded `prisma migrate deploy`; no db push, automatic resolve/baseline, shadow/reset or Development schema sync. No schema or migration changes in this integration.

Workflow: empty/unbaselined application schema → explicit database preflight → independently verified recent backup → guarded deploy → checksum/status/drift/audit verification → readiness. Commands and operator/governor safeguards are in PRODUCTION-DEPLOYMENT.md. Runtime and Replit publish have no migration authority. Local advisory-lock tests exercise real PostgreSQL with the same pg/Prisma stack, backend continuity, governance lock serialization, rollback release and session/prepared behavior; they verify compatibility assumptions, not a live Neon service.

## Upstash distributed authority

Production uses Upstash REST, no new SDK/package. Security-sensitive mutations await one atomic Redis EVAL: opaque SHA-256 User key + closed policy namespace + bounded quota + 60-second server TTL. First admission creates the expiry; blocked calls cannot inflate the counter. Existing policies/limits remain: learning/academic 120, upload/support/referral 10, discussion 20, communication 5 per minute. Admin/governance callers retain their existing policy assignment. No raw session/User identifier, request body or role claim becomes a key. Stable cross-process keys make VM restarts/instances share authority.

Missing/unavailable authority rejects writes UNAVAILABLE (503); exhausted quota rejects RATE_LIMITED (429). No process-local Production fallback or request replay. Local/test retain the bounded local implementation and reject Production provider credentials. REST POST uses HTTPS allowlisted Upstash hostname, bearer header, redirect rejection, 2-second deadline and 8-KiB response ceiling. Redis reply and TTL are validated. Readiness uses an expiring fixed write/EVAL probe (one 10-second key), not PING alone, and coalesces with the database probe for five seconds. Missing both credentials allows diagnostics/reads while readiness remains 503 and writes deny; partial/malformed configuration is a configuration error. Redis outages do not deliberately gate ordinary reads. Set RATE_LIMIT_BACKEND=upstash explicitly in deployment. [Upstash REST](https://upstash.com/docs/redis/features/restapi), [EVAL](https://upstash.com/docs/redis/sdks/ts/commands/scripts/eval).

Synthetic tests mock the atomic backend and exercise two limiter instances, shared quotas/expiry and failures. A live Redis/Lua/provider latency/quota test remains required later. Rate limiting complements authorization and Clerk protection; it does not replace ingress body/unauthenticated abuse controls.

## Better Stack and readiness

Safe structured JSON continues to stdout/stderr for Replit. Better Stack forwards through the same closed projection, projected again at the transport boundary: server UUID, masked route family, approved domain label, safe event/code/status/duration, timestamp and fixed Production/Node context. It never forwards exception diagnostics, bodies, cookies, headers, credentials, signed URLs, answers, Support text or file contents. Source URL is the dashboard-issued HTTPS s<source-id>.<region>.betterstackdata.com endpoint with no credentials/query; source token is header-only. Successful ingestion responses are discarded. [Better Stack HTTP ingestion](https://betterstack.com/docs/logs/ingesting-data/http/logs/) and [documented source ingesting_host](https://betterstack.com/docs/logs/api/get-a-single-source/).

Best effort: 2-second deadline, at most four in-flight sends, no queue/retries, 30-second cooldown on error, never awaited by product requests. Saturation/outage can lose external logs; stdout remains. Optional missing/bad observability configuration does not gate startup/requests/readiness. Provider/platform access logs are independent and require privacy review/retention/alert configuration; this adapter cannot redact their output. Structured logs do not replace immutable AcademicAudit. Verify Replit monitoring/logs and Better Stack receipt/correlation/outage alerts later.

Readiness requires valid Production configuration, verified database connectivity/identity/public schema, all eleven successful checksums, core tables and enabled audit immutability guards, plus available write-capable Upstash. Better Stack is excluded. Optional P2 states are explicitly NOT CONFIGURED and local filesystem is NOT PRODUCTION READY in operator preflight, rather than exposing internals on public probes. Ready P1 infrastructure is **not** approval to launch unsupported media, recording, certificate rendering or delivery. Replit filesystem never holds durable Production LMS files.
