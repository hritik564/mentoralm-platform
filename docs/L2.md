# L2 — Learning experience implementation report

Local implementation and validation on 2026-10-01. L2 only; no deployment, push, DNS change, production database connection or L3 implementation. D1–D4 and L1 authorization remain in place.

1. **Course Player architecture:** `/learn/courses/[courseId]` and `/learn/courses/[courseId]/lessons/[lessonId]` share `CoursePlayer`. Server projections supply the published, explicitly ordered Course → Section → LearningItem outline and selected authorized Lesson. The L1 horizontal shell stays intact; unsupported item types remain visible without executable actions. Production LMS-host rewriting and safe handoff support equivalent short paths on `students.mentoralm.com`.
2. **Lesson formats:** Versioned structured TEXT blocks (heading, paragraph, list, callout, code, divider); native controlled MP4/WebM VIDEO with optional protected WebVTT captions; sandboxed PDF viewer with separate-tab fallback; responsive raster IMAGE with alt text; approved EXTERNAL destination IDs. No arbitrary stored HTML, iframe embeds, autoplay or heavyweight player dependency.
3. **Content/media delivery:** PostgreSQL stores metadata and structured text, never media binaries. Separate protected media requests stream an authorized private file, support single byte ranges and enforce MIME/signature checks, path containment, limits, no-store/nosniff headers and configured download permission. Shared file primitives preserve separate Dashboard Resource and LMS authorization. Missing/invalid provider content has an honest unavailable state; an image/video failure occurring before hydration is also detected. Inline delivery is not DRM.
4. **Learning-state persistence:** `LessonState` has a unique `(userId,itemId)` key, actual Lesson foreign key, server-owned first/last access timestamps and nullable completion timestamp. Meaningful selected-Lesson navigation posts access once; GET/prefetch/render does not mutate learning state. Access and completion survive reloads and are scoped to the authenticated MentoraLM student.
5. **Completion behavior:** Explicit **Mark Complete** only. Serializable transactions, bounded conflict retries and constraints make repeated/concurrent requests idempotent without duplicate rows or changing the first completion time. Entitlement, own Enrollment, publication and available lesson content are rechecked server-side. No watch-percentage claim, final academic completion, Enrollment COMPLETED mutation or certificate eligibility.
6. **Progress engine:** One typed LMS projection derives Section/Course **Lesson progress** from completed required published Lesson records divided by all required published Lessons with Lesson metadata. Optional lessons and unsupported future item types do not enter the denominator. Empty denominators return no percentage. Published-content changes recalculate the projection. This is the L2 contributor boundary; L3 completion sources must join the aggregator rather than treating lessons as final Course completion forever.
7. **Continue Learning:** Ordered curriculum chooses a valid last-accessed incomplete Lesson, otherwise the first incomplete required Lesson, then an incomplete optional Lesson, otherwise Course overview. Access timestamp ties use Lesson ID; course summaries sort by actual last access with deterministic Course ID ties. Home, player and Dashboard consume the same rules.
8. **Dashboard integration:** Dashboard reads LMS summaries and resolves an approved Course/Lesson destination through the existing launch boundary. It displays actual Lesson progress and next Lesson when records exist; it does not calculate progress independently or write learning state. Denied entitlement removes the learning projection/launch while preserving ordinary Dashboard access. Student ID and Batch details remain LMS-only.
9. **LMS Resources:** Minimal `LearningResource` metadata specializes published RESOURCE LearningItems. Course overview and Learn → Resources list authorized Section/Course materials with controlled view/download actions and empty/unavailable states. Resource subtype and relationship constraints are enforced. This does not populate or authorize the general Dashboard Resource library.
10. **Mobile/tablet:** Below 1000px the curriculum becomes a Course Outline modal drawer; focus trapping, Escape, focus return, scroll locking and aria state are implemented. Course/lesson context, progress and Previous/Next remain usable without horizontal overflow at 1440, 820 and 390px. Six requested visual screens were inspected; captures are local, ignored files under `docs/reviews/l2/`. Representative axe scans passed; native media controls and content descriptions remain accessible.
11. **Security protections:** Every protected read/write derives the verified Clerk student and rechecks MentoraLM entitlement, Enrollment, Course and published content. Current business data enforces revocation. IDs do not authorize access; draft/unrelated/guessed content and another student's state are excluded. Strict empty mutation payloads reject client ownership, progress, timestamps and mass assignment; same-origin JSON validation rejects CSRF. Safe blocks escape text, external links use exact approved HTTPS registry destinations, and generic errors do not disclose storage paths/SQL/ownership reasons. Traversal, unsafe MIME and invalid signatures are rejected. No student entitlement, membership or Enrollment mutation API was added.
12. **Database migration:** Additive `20261001030000_lesson_delivery_progress` applied to local `mentoralm_dev` without reset. Five migrations are up to date. Added required/optional item policy, structured Lesson/media metadata, `LessonState` and `LearningResource`, with subtype, date and JSON-size checks. Clean isolated `mentoralm_test` schemas migrate successfully; populated legacy upgrade preserves existing user/Clerk/profile/Student ID, batch membership and curriculum. Database harness requires opt-in, a local `_test` database distinct from development, connected identity verification and random isolated schemas before destructive operations.
