# L1 — LMS foundation implementation report

Status: complete locally on 2026-10-01, including the domain/access addendum. D1–D4 remain in place. No L2 implementation, production database connection, push or deployment.

1. **Routes/shell:** Protected local/internal `/learn`, `/learn/lectures`, `/learn/assignments`, `/learn/resources`, `/learn/discussions`, `/learn/chat` and `/learn/courses/[courseId]`. Horizontal Home/Learn/Chat/Support navigation, Learn subnav and existing account/profile/support destinations. Locked production LMS is `students.mentoralm.com`; website/module pages and Dashboard remain on `mentoralm.com`. Approved origin configuration enables host rewrites and controlled cross-domain links in this same application. Home and course discovery use real server data; later functionality has honest unavailable states.
2. **Student ID:** PostgreSQL trigger and global bigint sequence issue `MLM-STU-YYYY-NNNNNN` with UTC issuance year and at least six serial digits. Unique, immutable, automatically backfilled, independent of internal/Clerk IDs. Sequence gaps are valid; no annual reset or client assignment.
3. **Batch:** Unique code, name, status, optional dates and optional Program or Course scope; unscoped batches are supported. SQL enforces scope, code and date invariants. Future Admin owns management.
4. **Membership:** Unique student/batch relationship supports multiple cohorts, ACTIVE/INACTIVE membership and joined/left timestamps. Current batch requires active membership and batch within inclusive dates; latest start wins, then code, with null starts last. Other memberships remain visible. No student assignment or switching APIs.
5. **Instructors:** Distinct INSTRUCTOR role; many-to-many BatchInstructor permits multiple instructors. Role-aware foreign keys/checks enforce instructor assignments and student memberships. No instructor or Admin UI. Future role transitions must resolve incompatible relationship rows first.
6. **Curriculum:** Existing Program and Course remain separate. Ordered, publishable Section and mixed LearningItem records support LESSON, QUIZ, ASSIGNMENT, RESOURCE, LIVE_SESSION and ASSESSMENT. Unique positive positions ensure ordering. Lesson is metadata only, with format/storage key/duration; subtype invariants prevent attachment to other item types. No binaries, players or learning state.
7. **Handoff:** Dashboard enrollment snapshots resolve controlled LMS course paths, using the approved LMS origin when configured. Continue Learning can launch a real enrolled course without invented progress. LMS independently reauthorizes entitlement and enrollment on each request; completed-course presentation is preserved.
8. **Visibility:** Student ID and batch identity appear in LMS Home only, with real name/avatar and neutral no-batch/no-active-batch states. They are absent from Dashboard/public/account payloads. Internal student, membership and batch IDs are not projected.
9. **Migration:** `20261001005000_instructor_role`, `20261001010000_lms_foundation` and `20261001020000_lms_entitlement` applied successfully to local `mentoralm_dev`; all four migrations are finished with none rolled back. No reset. Clean isolated test migration and populated D4 upgrade/backfill both pass; repeat deploy is up to date. Development has zero students missing an ID and no LMS fixture batches/sections/items.
10. **Security:** Verified Clerk subject maps to the existing server-owned STUDENT actor. Draft content/storage keys are excluded. Entitlement defaults deny: nullable student ENABLED/DISABLED override wins over inherited batch access; otherwise any applicable enabled active batch grants workspace access. Current batch display is independent. Revocation is checked on subsequent requests and denied students see a Support-linked unavailable state. No student entitlement API or Clerk metadata authorization. Narrow redirects, strict profile validation, absent batch/role mutation APIs and generic errors preserve D4 boundaries.
