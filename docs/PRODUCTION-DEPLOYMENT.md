## Release commands prepared by P1

The production commands do not load `.env.local`. A secret manager must supply environment values. An explicit command is required; generic `db:migrate`/`db:migrate:dev` refuse without contacting a database. Local A1/A3/A4 migration and seed commands retain loopback/identity guards.

- `npm run prod:preflight -- --confirm-production-configuration`: offline configuration/release-manifest check, zero network connections. Reports unresolved providers and trafficReady=false.
- `npm run prod:db:preflight -- --confirm-production=DATABASE_NAME --expected-host=DIRECT_HOST --change-ticket=TICKET`: future explicit read-only database identity and migration-prefix preflight.
- `npm run prod:db:deploy -- --confirm-production=DATABASE_NAME --expected-host=DIRECT_HOST --change-ticket=TICKET --backup-reference=OPAQUE_BACKUP_ID --backup-timestamp=ISO_TIMESTAMP`: future guarded migration deploy, followed by checksum/status validation.
- `npm run prod:db:status -- --confirm-production=DATABASE_NAME --expected-host=DIRECT_HOST --change-ticket=TICKET`: requires complete verified migration history.

Uppercase symbolic arguments above must be replaced with separately verified non-secret operator inputs; these are not ready-to-run commands. `PRODUCTION_DATABASE_NAME`, `MIGRATION_DATABASE_URL` (direct/operator connection) and runtime `DATABASE_URL` (direct Neon connection beneath the bounded pg pool) must target the SAME database/cluster. P1 validates database name/schema and exact direct Singapore endpoint/port equality; provider operators must independently verify branch/role/grants. Pooled endpoints refuse. MIGRATION_DATABASE_URL belongs in the controlled operator job, not the serving VM.

Deploy requires a backup evidence reference and timestamp within 24h; this validates input freshness, not the existence or restorability of a backup. The operator must verify those independently. The script accepts only its three fixed operations, checks the exact eleven-file release/checksums, rejects unknown/failed/duplicate/changed/noncontiguous migrations and unbaselined nonempty schemas. It invokes only `prisma migrate deploy`; it cannot reset, db-push, migrate-dev, resolve, create/drop Test schemas or seed. Underlying CLI output/errors are withheld because it may contain connection diagnostics. Any failed deploy requires operator inspection via secure logs/runbook, never blind reset/retry.

## Failure/rollback

Keep traffic off on config, migration, readiness or smoke failure. Preserve backup/migration/audit evidence. Prefer a separately reviewed forward fix compatible with the old/new release. Reverting an application artifact is safe only after verifying schema compatibility. No automatic down/reset/resolve or destructive rollback exists. Restoring to a replacement isolated database requires tested backup, identity/Clerk correspondence, append-only history preservation and reconciliation of writes since the snapshot; do not silently replace or truncate live audit.
